# TaaDaa

A Todoist-inspired task manager, scoped down and made personal. Full design intent lives in `task-app-spec.md` — this file is the condensed, working-reference version for day-to-day building.

**Status: complete v1.** All 7 phases from the build order are done (see Scope Rules below) — quick-add, projects/sidebar, calendar, recurring tasks/subtasks, dark mode, PWA install/share-sheet, and Web Push notifications are all built and verified. Treat future work as **refinements and bug fixes to an already-shipped app**, not new feature builds — don't introduce new views, new data-model fields, or new architecture unless the user explicitly asks for a new feature. When in doubt, prefer the smallest change that fixes the actual problem.

## Stack
- React + TypeScript + Vite (frontend), standalone Node/Express (`server/`) for push notifications — two separate deployables, see Push Notifications below.
- Tailwind CSS v4 (CSS-first config via `@theme` in `src/index.css` — no `tailwind.config.js`)
- `vite-plugin-pwa` with the **`injectManifest`** strategy (not `generateSW`) — needed because the service worker (`src/sw.ts`) has custom `push`/`notificationclick` handlers, which `generateSW`'s auto-generated Workbox SW can't express. `workbox-precaching` is a direct dependency because `src/sw.ts` calls `precacheAndRoute` itself.
- `chrono-node` for natural-language date parsing
- `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities` for drag-and-drop (see Drag and Drop below) — chosen over a hand-rolled Pointer Events implementation (like the swipe-to-snooze gesture) specifically because it needed to support several drop-target types (calendar days, sidebar projects, sortable lists) at once
- `sharp` (devDependency) rasterizes `scripts/source-icons/logo-source.png` into every PWA icon size/variant `public/` needs — rerun `node scripts/generate-icons.mjs` after changing the logo, don't hand-export PNGs (see PWA section)
- Local storage for persistence (no database — tasks/projects never leave the browser; only *reminder schedules* get synced to the push backend, see below)
- Fonts self-hosted via `@fontsource/*` (offline-safe for a PWA — never load fonts from a CDN link)

## Palette — "Raspberry Moon" (light) + a dedicated dark palette (defined in `src/index.css` `@theme`)
Exact hex values are spec'd, not arbitrary — don't "improve" them without checking the spec first. **The dark-mode recolor is dark-mode-only** — light mode still uses the original Raspberry Moon values below unchanged; don't extrapolate new light-mode values without being asked.
- `cream` `#FAD6D5` (light) / `#141416` (dark) — base page background. `ink` `#2B2A28` (light) / `#E8E8ED` (dark) — body text.
- `heading` — a token distinct from `ink`, used only on H1 view titles (`text-heading`, no `dark:` prefix needed): `#2B2A28` light / `#F5F5F7` dark (brighter than body text in dark mode specifically).
- `raspberry` `#AD1357` light / `#D63C7A` dark — the one confident primary accent: active states, buttons, priority.
- `wordmark` — the small "TaaDaa" sidebar wordmark's color, deliberately a different shade from `raspberry` so it doesn't compete with active-state pink: `#AD1357` light / `#E8639F` dark.
- `rose` `#CC698F` light/dark — secondary accent; also the "done/calm" completed-checkbox color and the `tomorrow` half of the snooze action.
- `softpink`, `berry`, `dustyrose`, `magenta`, `blush` — supporting roles: `berry` colors the `#self-care` tag and the `next week` half of the snooze action, `magenta` colors `#fun`, top-of-scale priority, and due-date badges specifically (see Two Dates below), `dustyrose` is the Boyfie project's default and general sub-category tint.
- `sidebar`, `border`, `badge-bg`/`badge-text`, `quickadd`/`quickadd-border` — dark-mode-only surface tokens with no real light-mode design (their light values just mirror `cream`/`ink`-ish so they're inert until dark mode overrides them). `sidebar` colors the sidebar panel distinctly from the page background; `border` replaces the old `dark:border-white/10` opacity trick everywhere with a real color (`#2A2A2E`); `badge-bg`/`badge-text` give project-name chips a flat, uniform look in dark mode (`#3A2130`/`#E8A0C0`) instead of each chip using its own project-color tint — applied via `dark:!bg-badge-bg dark:!text-badge-text` (the `!important` Tailwind modifier, since the light-mode per-project tint is set via inline `style`, which normal specificity can't override).
- All accent tokens get overrides inside a `.dark { ... }` block in `index.css` (plain CSS custom-property overrides — every `bg-raspberry`/`text-rose`/etc. usage picks these up automatically in dark mode, no component changes needed).
- Priority tint scale (`priorityColor()` in `TaskItem.tsx`): level 1 → rose, level 2 → raspberry, level 3 → magenta — increasing intensity of one accent family, not four unrelated colors.

## Dark Mode
Manual toggle (`auto` / `light` / `dark`, `src/components/ThemeToggle.tsx`), defaulting to `auto` (system preference) until the user picks otherwise. Choice persists per device in `localStorage['taadaa.theme']`. Rendered inside `Sidebar.tsx`'s footer (below "export data"), not in `App.tsx`'s header row — `App.tsx` still owns the `useTheme()` state, just passes `pref`/`onChange` down as props.
- **Class-based, not media-query-based:** `index.css` uses `@custom-variant dark (&:where(.dark, .dark *));` so every `dark:` utility responds to a `.dark` class on `<html>`, not directly to `prefers-color-scheme`. `src/lib/useTheme.ts` keeps that class in sync — applying the stored pref on mount, and (only when pref is `auto`) listening for OS-level scheme changes live.
- A blocking inline script in `index.html` `<head>` sets the class before first paint, to avoid a flash of the wrong theme — keep it in sync with `src/lib/theme.ts` if the storage key or logic changes.
- `theme-color` meta tag is updated at runtime too (`applyThemeClass` in `theme.ts`, values `#FAD6D5` / `#141416`) so mobile browser chrome matches.

## Typography
- Sans (Inter) for UI/body text — legibility.
- Serif (Fraunces, italic) for section headers and view titles ("Today", "Upcoming", project names) — journal/stationery feel, not app-dashboard feel. Never use the serif for body copy or buttons.

## Voice / Micro-copy
Deadpan, dry, unbothered. Never cutesy or exclamation-heavy.
- All done: "Nothing left. Go be hot elsewhere."
- No tasks yet: "Blank canvas. Or you're procrastinating. Unclear."
- Overdue section label: "yesterday's problem" (not "OVERDUE!!")
- Empty project/day: "This one's quiet. For now."
- Completed task: vanishes from its list immediately (no lingering strikethrough), undo toast reads "Done. (undo)" — same quiet-removal pattern as delete, no confetti, no streaks.
- Loading state: "syncing," lowercase, no exclamation point or emoji.
- Small functional glyphs (priority flag, reminder bell, note paperclip, recurrence ↻) are plain SVG/Unicode, not colorful emoji — matches the hand-drawn-checkmark, non-gamified visual language. The "no emoji" voice rule is about copy, not these icons, but the effect should look the same: restrained.

## Data Model (`src/types.ts`)
- `Project { id, name, color, parentId, createdAt }` — one level of nesting (`parentId` on a sub-category points at a top-level project; a sub-category's own `parentId` is never itself set to another sub-category). Colors: `colorForNewProject()` in `src/lib/projectColors.ts` special-cases "Boyfie" → dusty rose (per spec), otherwise rotates through the accent palette; sub-categories store their *parent's* color and get tinted lighter at render time via `displayColorFor()` — never store a separately-tinted color, always derive it, so re-tinting logic lives in one place.
- `Task` gained `time` (optional "HH:MM", independent of `date`), `projectId` (replaces the old flat `project: string`), `priority` (`1 | 2 | 3 | null`), `reminders` (`ReminderRule[]`, 0-3 entries, each `{ leadMinutes }`), `note` (freeform text/link, no file uploads), `order` (`number | null` — see Drag and Drop below), and `completedAt` (`number | null`, a `Date.now()` timestamp set by `toggleTask` in `useTasks.ts` on completion and cleared back to `null` on un-complete) on top of the existing fields. `completedAt` exists purely to sort the Completed view and search results by recency — nothing else reads it. Tasks saved before this field existed just have it `undefined`; every reader treats that the same as `null` (falls back to `createdAt`) rather than requiring a migration.
- **Two dates per task**: `date` is the "work on" date — it's what drives calendar placement and Upcoming's "Tasks" column. `dueDate` is the actual deadline, the harder constraint, and drives Upcoming's "Deadlines" column. Displayed distinctly: `date` renders as plain muted text, `dueDate` renders as a magenta pill (bolder/filled once it's actually passed and the task isn't done). Both are settable from the same calendar-icon popover in the quick-add toolbar and from `TaskEditModal` (two side-by-side date inputs, "Work on" / "Due date"). Neither ever renders as a raw ISO string under a `TaskItem` row — `formatRelativeShort()` in `src/lib/date.ts` collapses it to `yest` / `today` / `tomorrow`, falling back to `dd/mm` for anything further out; `TaskEditModal`'s own date `<input type="date">` fields are unaffected, since those need the real ISO value to round-trip.
  - **`TodayView`'s "yesterday's problem" section is deliberately broad**: it fires if *either* `date` or `dueDate` is in the past (`!done && ((date && date < today) || (dueDate && dueDate < today))`), by explicit request, so a slipped work-on date surfaces there too, not just a missed deadline. (An earlier `HomeView` had a narrower, `dueDate`-only overdue section here too, which made this asymmetric between the two views — moot now that `HomeView` is gone, but flagged in case that history matters if overdue logic changes again.)
  - **"due `<date>`" / "due on `<date>`" / "due by `<date>`" NLP parsing**: `parseQuickAdd.ts` recognizes all three phrasings (`DUE_MARKER_RE`, the "on"/"by" is optional) and parses the date after the marker into `ParsedQuickAdd.dueDate`, stripping the whole "due [on/by] `<phrase>`" span from the title — separate from the normal work-on `date` parse, which still runs on whatever text is left. Bare "due" was originally excluded entirely (too likely to appear in ordinary titles like "card payment due to a billing issue") but was reinstated by request — the false-positive risk is actually handled by a different guard that already existed: the marker only *commits* to a due date if chrono finds an actual parseable date immediately after it (`dueResults.length > 0`); "due to a billing issue" never does, so it still falls through safely with the title untouched.
  - **Calendar-day-selected → deadline default**: `CalendarView`'s selected day is lifted to `App.tsx` (`selectedCalendarDate` state, passed down as `selected`/`onSelectDate`) so `handleAdd` can default a new task's `dueDate` to it — clicking a day and adding a task there makes that day the deadline, not the work-on date, since the calendar itself is a date-driven planning surface, not a "what am I doing" list. Only applies while `view.kind === 'calendar'`, and only as a fallback (`submission.dueDate ?? selectedCalendarDate`) — an explicit "due on" phrase or manual toolbar due-date still wins.
  - **Project-view quick-add auto-files into that project**: while viewing a specific project (`view.kind === 'project'`), `handleAdd` defaults `projectId` to `view.projectId` as the lowest-priority fallback (an explicit `@project` in the text, or the toolbar's manual project picker, still wins). Mirrors the calendar-deadline default's fallback pattern.
- **`useProjects.ts`'s `resolveProjectPath()`** turns a raw `"@Home/Groceries"` string into a leaf project id, auto-creating the parent and/or sub-category if they don't exist yet — same "frictionless, no dropdown required" philosophy as tags. One level deep only (a third `/segment` is silently ignored). Reads current `projects` state synchronously and returns the id immediately rather than trying to read anything back out of `setProjects`'s updater — see the React gotcha note under Undo Toast; the same rule applies here.

## Navigation & Views
Sidebar-driven, not tab-driven — `src/lib/viewState.ts` defines `ViewState` (`inbox | today | upcoming | calendar | completed | { project: id }`), owned by `App.tsx`, rendered by `src/components/Sidebar.tsx`.
- **Desktop:** sidebar is a fixed always-visible column (`hidden sm:block`). **Mobile:** hidden behind a hamburger button (`☰`, top-left) that opens a slide-in drawer with a dimmed backdrop — same `Sidebar` component in both places, just two different wrapping containers in `App.tsx`.
- A small serif "TaaDaa" wordmark sits at the top of the sidebar (its own `wordmark` color token, see Palette above) — purely a brand label, not a link.
- Sidebar has pinned links (**Inbox**/Today/Upcoming/Calendar/Completed, in that order) above a collapsible Projects list (color dot + name + subtle pending-count, sub-categories nested and collapsed by default, indented `ml-9` under their parent — bumped up from `ml-5`, which visually canceled out against the parent row's own arrow-toggle spacer and left sub-categories flush with their parent's text instead of looking indented at all), then sync settings, notification toggle, and an "export data" button pinned to the bottom (`mt-auto`).
- **There is no "Home" view.** An earlier revision had one (a project-grouped next-7-days overview) and used it as the default landing view; it was removed by explicit request, not merged into anything — **Today is now the default landing view** (`App.tsx`'s `useState<ViewState>({ kind: 'today' })`, and `handleDeleteProject`'s fallback when the currently-viewed project gets deleted). Its "next 7 days" framing lives on in Upcoming's redesign below instead of a project-grouped overview. Don't reintroduce a `HomeView.tsx` / `{ kind: 'home' }` without checking first — this was a deliberate removal, not an oversight.
- **Each pinned view has a genuinely distinct filter now** — an earlier revision had Today/Upcoming overlapping (Today included future-dated tasks too), which defeated the point of having separate tabs. Current split, by design:
  - **Inbox** (`InboxView.tsx`) — a pure capture bucket: no project **and** no date/due-date at all (`projectId === null && date === null && dueDate === null`), sorted newest-first. The moment either field gets set, the task graduates to a planning view instead.
  - **Today** (`TodayView.tsx`) — the default landing view. "yesterday's problem" (overdue by either date, see the Data Model note above) stays one deliberately-broad full-width section — splitting it would fight its whole point (either date type slipping counts as overdue). Below it, "today" splits into the same Tasks/Deadlines column pair Upcoming uses (below): Tasks = `date === today`, Deadlines = `dueDate === today`, both excluding anything already caught by the overdue section above. A task due today *and* scheduled to work on today shows in both columns, same duplication rule as Upcoming.
  - **Upcoming** (`UpcomingView.tsx`) — **two independent columns, not one merged list**: "Tasks" (`date` in `(today, today+7]`) on the left, "Deadlines" (`dueDate` in `(today, today+7]`) on the right — stacked vertically instead of side-by-side below the `sm` breakpoint. Bounded to the next 7 days now (was unbounded — every future task, no matter how far out); still excludes today itself, same as before, since Today owns today. A task with both a work-on date and a deadline inside the window can legitimately appear in *both* columns — they're answering two different questions ("when am I doing this" vs. "when is this actually due"), not partitioning the same list. Each column sorts independently by its own date field; there's no cross-column merge or single chronological ordering anymore.
  - **`TaskColumn.tsx`** is the shared column renderer behind both splits above (label, empty-state copy, and a list rendered through the usual `TaskItem`) — extracted once a second near-identical copy showed up, not before. Today's `Section` component (the "yesterday's problem" renderer) stays separate rather than also going through `TaskColumn`, since it needs its own internal `sortChronological()` call and serif-italic heading style that the two-column split doesn't use. Today and Upcoming both get a wider container (`max-w-3xl`, via `containerWidthClass()` in `App.tsx` — see below) since two side-by-side columns need more room than the other single-column list views.
  - **Calendar** — unchanged, the spatial week/month grid, for visual planning rather than a list.
  - **Completed** (`CompletedView.tsx`, added after v1 shipped — see Scope Rules) — the one deliberate exception to "completed tasks disappear immediately, everywhere" below: a flat, most-recent-first archive of every `done` task (`t.completedAt ?? t.createdAt` descending), no project grouping, no nesting for done subtasks. Un-checking a task here vanishes it from this list too, same instant-removal convention as every other view — this isn't a strikethrough history log, it's "everything currently marked done," which just happens to be nothing *but* done tasks by construction.
- **Project view** (`ProjectView.tsx`) shows a flat list of one project's own tasks (exact `projectId` match only — selecting a parent project does *not* also pull in its sub-categories' tasks; drill into the sub-category itself via the sidebar for that).
- **Project management** (add/rename/delete) lives directly in the sidebar's Projects section (`Sidebar.tsx`), not a separate settings screen: a "+ add" link next to the "Projects" header opens an inline name input (same pattern as the "+ subtask" affordance); each row reveals a rename (✎) and delete (✕) affordance on hover, matching `TaskItem`'s hover-reveal convention. Rename is an inline text swap (auto-save on blur/Enter, no separate Save button — consistent with the rest of the app). Delete asks a native `window.confirm()` first — the same deliberate exception to "no confirmation dialogs" as joining a sync code, since it's rare and only mildly reversible — then calls `useTasks.ts`'s `unassignProject()` to clear `projectId` (set to `null`) on every task under that project (and, if it's a top-level project, its sub-categories too) *before* removing the project itself, so tasks survive as unfiled rather than pointing at a dangling id or vanishing. `useProjects.ts` exposes `addProject`/`renameProject` alongside the existing `deleteProject`.
- All list/group views funnel through the same `TaskItem` component, so completion/delete/subtask/edit/snooze behavior never diverges by view.
- **Completed tasks disappear immediately, everywhere** — every list/group view (Inbox, Today, Upcoming, Project view, Calendar's day cells and selected-day panel) filters to `!t.done` before rendering, rather than rendering a done task in place with strikethrough/fade styling. `handleToggle` in `App.tsx` still fires the "Done. (undo)" toast, so completing is instantly reversible the same way delete already was. Two deliberate exceptions, both added later by request: the Completed view (below) is *only* done tasks, and `SearchOverlay` shows both — everywhere else, this rule holds.
- **Chronological sorting everywhere a list actually has dates.** `sortChronological()` in `src/lib/sortTasks.ts` (key: `date ?? dueDate`, then `time` as a tiebreak) governs Today's sections, Calendar's selected-day panel and day-cell previews, and Project view. Upcoming's two columns each sort independently by their own single date field (`dueDate` for Deadlines, `date` for Tasks) rather than this shared helper, and Inbox stays newest-first by `createdAt` (its tasks are dateless by definition, so there's nothing to sort chronologically).
- **No project is pre-seeded on a fresh install.** `useProjects.ts`'s `loadProjects()` just reads `localStorage` — it used to auto-create a "Personal" project (with Errands/Shopping/Admin sub-categories) if one didn't exist, but that's been removed by request. Existing installs that already have a "Personal" project from before this change keep it (nothing deletes existing data); it's just not created for anyone new. Delete it manually via the sidebar's hover-revealed ✕ if you don't want it.
- **Quick-add is fixed to the bottom of the screen** (`App.tsx`, `position: fixed; inset-x-0; bottom-0`, offset past the sidebar's width on desktop via `sm:left-56`), not part of the scrolling content — main content gets bottom padding (`pb-28`) so nothing sits underneath it. `Toast` had to move its offset up to `bottom-28` to clear this bar (it used to sit at `bottom-6`, which now overlaps the input).
- **Sidebar and main content scroll independently.** The outermost layout div is `h-svh overflow-hidden` (was `min-h-svh`, which let the whole page grow and scroll as one whenever content overflowed — the sidebar's background would visibly stretch to match, since it's a flex sibling of the same row). Now the row itself is pinned to exactly the viewport height; the sidebar's own `nav` (`h-full overflow-y-auto` in `Sidebar.tsx`) and the main content wrapper (`min-h-0 flex-1 overflow-y-auto` in `App.tsx`) each own their own scroll independently. `min-h-0` on both the main column and its scrollable child is required — without it, a flex child's default `min-height: auto` refuses to shrink below its content size and overflow-y-auto never actually kicks in.

## Search
`SearchOverlay.tsx`, opened via the magnifying-glass icon in the header (next to the shopping-bag icon, both visible on mobile and desktop). Added after v1 shipped, by explicit request — see Scope Rules.
- The one place in the app that looks *outside* whatever view is currently open: a case-insensitive substring match on `task.title` across every task, top-level or subtask, done or not — title only, no note/tag/project matching, kept deliberately minimal for a first pass.
- Sort: not-done matches first (by `chronoDate()`, soonest first — same key `sortChronological()` uses), then done matches (most recent `completedAt` first, same key `CompletedView` uses).
- Renders results through the same `TaskItem` component as every other view (checkbox/delete/subtask/edit/snooze all work directly from a result), but with `draggable={false}` — dragging a result out of a transient overlay to reorder/reassign didn't make sense contextually, and disabling it sidesteps needing to wrap results in their own `SortableContext` (same pattern `TaskItem` already uses for nested subtask rows).
- Same slide-in-from-the-right panel structure as `ShoppingDrawer` (dimmed backdrop, click-to-close, `Escape` to close) — reused rather than inventing a second overlay pattern.
- Empty states follow the app's deadpan voice: "Start typing to find a task." before any input, "Nothing matches. Try different words." for a query with no hits.

## Task Editing
Click any task's title/body (not the checkbox or delete ✕) to open `TaskEditModal.tsx` — a bottom sheet on mobile, centered dialog on desktop. Every field **auto-saves on change** (no Save/Cancel buttons) via `updateTask(id, changes)` in `useTasks.ts` — consistent with the app's "no confirmation dialogs for routine actions" stance; closing the modal is just dismissal, not a commit step. Delete is available inline at the bottom.

## Quick-Add Toolbar
`QuickAdd.tsx` still parses free text first (date/`@project`/`#tag`/recurrence via `parseQuickAdd`), but now has an icon row underneath (folder/calendar/clock/flag/bell/paperclip, from `src/components/icons.tsx`) that layers manual overrides on top — clicking an icon opens one inline panel below the row (only one at a time; simpler and more robust than floating popovers, especially on mobile) for project/date/time/priority/reminders/note. Icons go from muted to raspberry-filled once a value is set, mirroring the spec's "icons light up in the accent color" requirement.
- At submit, `App.tsx`'s `handleAdd` merges: manual date wins over parsed date; manual project id wins over the parsed `@project` text (which still gets resolved via `resolveProjectPath` if no manual override was picked); everything else (priority/time/reminders/note) is purely manual since text parsing never sets those.
- The subtask inline input (in `TaskItem.tsx`, opened via the hover "+" icon next to the clock — see Subtasks below) has **no** toolbar — it still only runs through `parseQuickAdd`, so date/`@project`/`#tag` work there but priority/reminders/note don't. Deliberately kept minimal; add the toolbar there too if subtasks turn out to need it in practice.

## Quick-Add Syntax
Parsed from a single free-text input (`src/lib/parseQuickAdd.ts`):
- Natural-language dates via chrono-node ("tomorrow", "next tuesday", "in 3 days", etc.)
- `@ProjectName` or `@ProjectName/SubCategory` — resolved to a project id at add-time via `resolveProjectPath` (see Data Model above), not inside the parser itself, since the parser has no access to the current projects list.
- `#tag` — freeform calendar-highlight tag, independent of project. Defaults ship pre-colored: `#fun` → magenta, `#social` → rose, `#self-care` → berry (see `src/lib/tags.ts`). Unknown tags fall back to a muted neutral dot color — always give new tags *some* color rather than none.
- Whatever text remains after stripping the above becomes the task title.
- **chrono-node gotcha:** bare time-of-day words ("night", "morning", "evening", "afternoon", "noon", "midnight") get masked out before parsing (`maskAmbiguousTimeWords` in `parseQuickAdd.ts`). Without this, chrono anchors on the word alone and silently swallows an adjacent relative phrase — e.g. "game night in 3 days" was resolving to *today*, not +3 days, and mangling the title down to "game". Safe to mask because the app never stores time-of-day *in the date parser* (the toolbar's separate time field is unaffected). Compound words like "tonight" are unaffected (word-boundary regex). Keep the `hasDateComponent` filter (uses chrono's `isCertain()`) if you touch this file — it rejects matches chrono only guessed rather than actually parsed.
- **Natural-language time**: `ParsedQuickAdd.time` ("HH:MM" or null) is now parsed alongside `date`, not just settable manually via the toolbar's clock icon. A combined phrase like "tomorrow at 5pm" gets both from the *same* chrono match (checked via `result.start.isCertain('hour')`) since chrono already parses the whole span as one result. A bare time with no date component ("call mom at 5pm") never satisfies `hasDateComponent`, so it's never in that first, date-filtered result set — a second, unfiltered chrono pass over the remaining text catches it (only when `time` is still null after the first pass, so it doesn't double-consume a combined phrase). `QuickAdd.tsx`'s submit merges `manualTime ?? preview.time`, same precedence pattern as manual date over parsed date. Deliberately tied to `date` only, not `dueDate` — there's no separate "due time" field in the data model, so a "due on/by" phrase's time (if any) is currently ignored, matching the existing single-`time`-field design.
- **Recurrence phrases** ("every day", "every week", "every N days/weeks", "every monday") are parsed by `src/lib/recurrence.ts` *before* chrono ever sees the text. **Deliberately no bare "daily"/"weekly" adjective support** — only full "every X" phrasing triggers recurrence, because bare `/\bdaily\b/` used to also match inside ordinary titles like "daily standup", silently corrupting them. Don't re-add bare adjective matching without solving that ambiguity first.
- **Priority shorthand**: a standalone `!`/`!!`/`!!!` token sets priority 1/2/3 (`PRIORITY_RE` in `parseQuickAdd.ts`, more bangs = higher priority, clamped at 3 for longer runs). "Standalone" means bounded by whitespace/start/end — `!` glued directly to the previous word (`"we won!"`) doesn't match, specifically so an ordinary exclamatory title doesn't silently acquire a priority. Manual toolbar priority still wins over the parsed value (`manualPriority ?? preview.priority` in `QuickAdd.tsx`, same precedence pattern as date/time), and the subtask inline input and the PWA share-target capture both pick up the parsed priority too, same as they do for `time`.

## Recurring Tasks
`src/lib/recurrence.ts` — model is intentionally minimal: `{ freq: 'daily' | 'weekly', interval: number }`, no day-of-month or multi-weekday rules.
- Completing a recurring task (`toggleTask` in `useTasks.ts`) marks that instance done *and* spawns a fresh not-done instance dated `nextOccurrence()` away — same title/project/tags/recurrence, new id. History is preserved (you can see past completions), unlike editing the date in place.
- Un-completing (toggling back) does **not** retract the spawned next instance — there's no linkage tracked between occurrences. Deliberately skipped for V1 simplicity; the undo *toast* (not manual re-toggle) does retract it, since it precomputes the spawned id up front.
- Displayed as a small "↻ every day" style chip in `TaskRow` (inside `TaskItem.tsx`) and in the quick-add preview.

## Subtasks
One level deep only, enforced by convention rather than the type system: `Task.parentId` points at a parent, and a subtask's own `parentId` is never itself set to another subtask.
- Bucketing/grouping logic everywhere (`TodayView`, `UpcomingView`, `ProjectView`, `CalendarView`) filters to `parentId === null` for top-level placement — a subtask's own `date` is cosmetic only right now, it never causes the subtask to appear in its own bucket/group. It's always rendered nested under its parent, wherever the parent lands.
- Add via a small "+" hover-revealed icon in the top-level `TaskRow`, sitting next to the clock (snooze) icon — desktop-only, matching that icon's own `hidden ... sm:block` hover-reveal pattern. (This replaced an earlier always-visible "+ subtask" text link rendered below the row; moving it into the hover row keeps the row itself the only "add a thing here" affordance instead of a separate persistent link underneath.) Clicking it still opens the same inline text input as before, wired through `onAddSubtaskClick` on `TaskRow` down to `TaskItem`'s own `addingSubtask` state.
- Deleting a parent (`deleteTask` in `useTasks.ts`) cascades to delete its subtasks too.

## Calendar View
`src/components/CalendarView.tsx` — toggles between **week** (Monday–Sunday) and **month** grid layouts. Both layouts share the same `DayCell` rendering so the visual language never diverges.
- Day cells are big enough to show content directly, not just a tap target: each shows the day number (today gets a filled raspberry circle) plus up to `maxTitles` task titles inline, truncated, with a "+N more" line if there are more. Week cells fit 4 titles, month cells fit 2 — deliberately fewer in month layout since there are up to 6 rows competing for vertical space. Done tasks are filtered out entirely (see "Completed tasks disappear" above), so nothing here needs its own done/strikethrough state.
- **A day's tasks are the union of what's worked-on and what's due that day** (`t.date === iso || t.dueDate === iso`) — a task with a `dueDate` but no `date` used to be invisible on the calendar entirely; now it surfaces on its deadline day. Per-title styling signals which kind it is: a task due *that* day gets a blue ring/box around its title (`ring-blue-400`, a deliberate one-off use of blue outside the app's usual accent palette, specifically requested for this), a title containing "exam(s)", "quiz(zes)", "test(s)", or "internal(s)" (`RED_FLAG_RE` in `CalendarView.tsx`, word-bounded so "example" doesn't false-positive on "exam") gets an automatic red ring — no tag or manual step needed, just one of those words in the title — a `#fun`-tagged task gets a pink/raspberry ring, and anything else renders as bare text — no `@Project` prefix, no tag dot, no highlight. Precedence when more than one applies: red-flag wins over due-date blue, which wins over fun-pink — an exam/test with a deadline set should still read as "exam," not just "something due," so the red check runs first.
- **Bigger cells, more breathing room**: cell min-height is 112–132px (week) / 92–112px (month), internal padding `px-2 py-3`, grid gap `gap-2 sm:gap-3` — all bumped up from the original tighter spacing. `App.tsx`'s `containerWidthClass()` also gives this view alone the widest container (`max-w-5xl`, vs `max-w-3xl` for Upcoming's two columns and `max-w-xl` for every single-column view) so it actually uses the available desktop width instead of sitting in the same narrow column as the text-list views.
- The **heat-strip** is the day cell's own background tint — `heatClass()` washes the whole cell in raspberry at increasing opacity by task count (0/1–2/3–4/5+ tiers, never a number). A selected day overrides this with a stronger raspberry wash + ring instead of blending the two.
- Tapping a day selects it and shows that day's tasks below the grid — fully interactive there (checkboxes, delete, subtasks, snooze, click-to-edit), unlike the read-only inline preview in the cell itself. Empty day copy: "This one's quiet. For now."
- **Per-day note** (`useDayNotes.ts`, `localStorage['taadaa.dayNotes']`, keyed by ISO date): a small notebook-icon button next to the selected-day label toggles a textarea open — hidden by default per the request, not a persistent field, since it's meant to be rarely used. Icon goes from muted to filled rose once a note exists for that day. Deliberately separate from tasks (a day-level journal scrap, not a task field) and from `TaskItem`'s note field.
- Month grid pads with adjacent-month days (muted, still clickable) so every row is a full week — `getMonthGridDays()` in `lib/date.ts`.
- The faint dot-grid texture (`.calendar-texture` in `index.css`) is scoped to this view only.
- Undated tasks never appear here by design — the calendar is strictly date-driven.

## Drag and Drop
Built with `@dnd-kit` (see Stack above), wired through a single top-level `DndContext` in `App.tsx` — desktop-only throughout (the grip handle is `hidden ... sm:block`), matching the existing pattern of desktop-only affordances like the snooze clock-icon button.
- **Grip handle** (`GripIcon`, hover-revealed like the snooze/delete icons): dnd-kit's ref/transform go on `TaskRow`'s *outer* wrapper div; the swipe-to-snooze `translateX` stays on the *inner* row div, so the two drag systems never fight over the same transform. The handle's `onPointerDown` calls `stopPropagation()` before delegating to dnd-kit's listener, since without it grabbing the handle would also trigger the row's own swipe-to-snooze pointer handlers.
- **Drop zones**: a calendar day cell (`useDroppable`, `CalendarView.tsx`) sets the dropped task's `date` (or `dueDate` if Shift is held through the drop — tracked via a `shiftHeldRef` kept current by plain window keydown/keyup listeners, since `DragEndEvent` has no modifier-key field of its own); a sidebar project row (`useDroppable`, wrapped via a small `ProjectDropZone` component in `Sidebar.tsx`) reassigns `projectId`.
- **List reordering**: every place a task list renders is wrapped in a `SortableContext`, so any task is always a drag *source* for the drop zones above — but **no view persists a manual within-list order anymore.** Every list (Today, Upcoming's two columns, Inbox, Project view, Calendar's selected-day panel and day-cell previews) always displays chronologically (see "Chronological sorting" under Navigation & Views), by explicit request. `Task.order` and `reorderTasks()` in `useTasks.ts` still exist and `App.tsx`'s `handleDragEnd` still writes to `order` on a same-list drag (harmless, just currently unread by any view's render), kept rather than ripped out in case manual ordering is wanted back later — but right now dragging a task within its own list has no visible effect, same as it already didn't for Upcoming/Inbox/Project view before this change.
- **Visual feedback**: dragging scales the row to `1.02` + drops to 80% opacity + a raspberry glow (stronger in dark mode); a drop target under the cursor gets a `ring-2 ring-inset ring-raspberry` highlight.

## Undo Toast
`src/components/Toast.tsx` + state in `App.tsx`. Fires for completing a task (not un-completing) and for deleting a task. Single-slot, auto-dismisses after 4.5s. Copy is exactly "Done." / "Deleted." plus a separate "(undo)".
- **React gotcha, read before touching `useTasks.ts` or `useProjects.ts`:** `setState(prev => ...)` does **not** invoke the updater synchronously — React only *queues* it; the updater actually runs later, during reconciliation. Anything the caller needs to know *right now* (did this complete the task? what id did we just create?) must be decided by reading the already-current state array **before** calling the mutator, not by trying to extract a result from inside the updater afterward. This bit us once already (`toggleTask`/`deleteTask`'s undo-toast plumbing) and the same pattern is used correctly in `resolveProjectPath`.

## Snooze
`TaskItem.tsx`'s `TaskRow` — swipe left (mobile) or click the small clock quick-action button that appears on hover (desktop) reveals the same underlying two-button panel ("tomorrow" / "next week") sliding in from the right edge, rather than being two separate implementations. The row itself is `position: relative; overflow: hidden` with the action panel absolutely positioned behind it at `right: 0`; the row's own `translateX` (driven by `dragX` state, via Pointer Events so touch and mouse both work) slides left to reveal it. Tapping the row while it's revealed closes the panel instead of opening the edit modal — a swipe-list convention, not a bug. `App.tsx`'s `handleSnooze(id, days)` sets `date` (the work-on date, not `dueDate`) to today+1 or today+7 and shows an undo toast ("Snoozed to tomorrow." / "Snoozed to next week."), same quiet-undo pattern as complete/delete.
- **Hover-state bug, fixed**: the row's `:hover` background used to be a *translucent* `bg-ink/[0.03]` (`dark:bg-white/[0.04]`) layered on top of the base `bg-cream`. In CSS, `background-color` isn't additive — the hover value fully *replaces* the base one, so on hover the row's background actually became ~97% transparent, letting the always-mounted reveal panel underneath bleed straight through and visually collide with the row's own text/icons the moment you hovered (not just while dragged). Fixed by mixing the hover tint into a single opaque solid color at build time (`hover:bg-[color-mix(in_oklab,var(--color-cream)_97%,var(--color-ink)_3%)]`, and the dark-mode equivalent against `--color-cream-dark`/`white`), so the row stays fully opaque in every state. If you touch this row's hover styling again, keep it as one opaque `background-color` — never a translucent one — since this row specifically has non-decorative content sitting directly behind it.

## Offline Support
The app already worked offline in spirit before this was ever asked for — tasks/projects live entirely in `localStorage`, no network required for core CRUD. What was actually missing: **the dev server has nothing to precache** (`self.__WB_MANIFEST || []` is deliberately empty in dev, see PWA note below), so "does it work offline" can only be tested against a production build (`npm run build && npm run preview`, not `npm run dev`) — don't be fooled by a dev-mode offline test failing, that's expected. The other real gap: a push/sync request made *while offline* failed silently and never retried once connectivity returned. `App.tsx` now listens for the browser's `online` event and re-runs `syncReminders` and `pushSync` (if a sync code exists) at that point, so pending changes actually propagate instead of silently waiting for the next unrelated edit.

## Data Export & Import
Sidebar footer, "export data" button (`src/lib/exportData.ts`) — downloads a JSON file (`taadaa-export-YYYY-MM-DD.json`) containing `tasks`, `projects`, and `dayNotes`, built client-side via a `Blob` + a synthetic `<a download>` click, no backend involved.
- **"import data"** (`src/lib/importData.ts`, added after v1 shipped — see Scope Rules) sits right next to it, a hidden `<input type="file">` triggered by the visible button. `parseImportFile()` reads and JSON-parses the file, checking only that `tasks`/`projects` are arrays (`isImportPayload()`) — not a full schema validation, just enough to reject a random non-export JSON file with a plain-English error instead of silently corrupting state. On a valid file, a native `window.confirm()` gates the actual replace — the same deliberate exception to "no confirmation dialogs" as joining a sync code, since this is a rare, one-time, genuinely destructive action (silently discarding whatever was on the device already).
- **Wholesale replace via `localStorage.setItem` + `window.location.reload()`**, not React state setters — same "simplest thing that works" choice as the sync join flow, but reload is specifically needed here (unlike join) because the export payload also covers `dayNotes`, which has no prop-threaded replace path from `Sidebar.tsx` down to `CalendarView.tsx`'s own `useDayNotes()` instance. A full reload picks up every localStorage-backed store fresh, without needing to wire a new callback through props just for this one rare action.
- Still no conflict handling or partial/merge import — this is a full local replace, same one-way "whole-blob" philosophy as sync and as export itself.

## Push Notifications — built, needs your setup to go live
Real device notifications sent by TaaDaa itself, no Google account needed. **Frontend and backend are two separate deployables** — this was a deliberate architecture choice, not an accident: a reminder scheduler needs a persistent process checking "is anything due right now?", which doesn't fit Vercel's stateless serverless-function model, whereas a small standalone Node/Express server with a plain `node-cron` job is simple to reason about and can be hosted anywhere (Render/Railway/Fly.io/a VPS) independent of the Vercel-hosted frontend.

**Pieces:**
- `src/sw.ts` — custom service worker (`push` / `notificationclick` handlers), built via `vite-plugin-pwa`'s `injectManifest` strategy (see Stack note above). In dev mode `self.__WB_MANIFEST` is never injected (no build has happened), so it's precached with `|| []` — omit that fallback and the dev service worker throws on evaluation and silently fails to register.
- `src/lib/push.ts` — `subscribeToPush()` / `unsubscribeFromPush()` (permission request + `pushManager.subscribe()` + POST to the backend), and `syncReminders(tasks)` which flattens every not-done task's `reminders` into `{id, title, fireAt}` payloads (task with no `time` defaults to 09:00 on its due date) and POSTs the full set to the backend, replacing what was there — simplest sync model, no incremental diffing. Called from a `useEffect` in `App.tsx` on every `tasks` change; it's a no-op if there's no active subscription yet.
- `src/components/NotificationToggle.tsx` — the enable/disable button, pinned to the bottom of the sidebar. Only renders if `isPushSupported()` (checks for the Push API *and* that `VITE_VAPID_PUBLIC_KEY`/`VITE_PUSH_API_URL` env vars are set).
- `server/` — standalone Express app (**own `package.json`, own `node_modules`, run separately from the frontend**). `db.js` is a plain JSON-file store (`server/data.json`, gitignored) — plenty for a personal app, no hosted database needed. `index.js` exposes `POST /api/subscribe`, `POST /api/unsubscribe`, `POST /api/reminders` (replace-all for one subscription), `POST /api/test-push` (send immediately, bypassing the schedule — used for testing and could back an in-app "send test notification" button later), and runs `node-cron` every minute to find due reminders and send them via `web-push`. On a genuine 410/404 (subscription gone) it deletes the subscription; on any other send failure it deliberately leaves the reminder unsent so the *next* minute's tick retries it, rather than silently dropping it — a real transient FCM hiccup during testing got lost before this fix.

**Local setup (already done in this repo, for reference):**
1. VAPID keys generated via `npx web-push generate-vapid-keys` — public key is in root `.env` as `VITE_VAPID_PUBLIC_KEY`, both keys are in `server/.env` (`VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT`). Both `.env` files are gitignored — regenerate your own keys if you ever suspect these leaked.
2. `cd server && npm install && npm start` runs the backend on port 4000 (`PORT` in `server/.env`).
3. Frontend's `VITE_PUSH_API_URL=http://localhost:4000` in root `.env` points at it. `npm run dev` as usual.

**Verified end-to-end** (Playwright + real Google Chrome, not Playwright's bundled Chromium — see caveat below): subscribed a real browser, POSTed a reminder with a past `fireAt`, watched `node-cron`'s next tick send it via `web-push` to Google's FCM, and confirmed the service worker's `push` handler actually called `showNotification` with the right title/body.

**Known caveats:**
- **Playwright's bundled/open-source Chromium cannot complete a real push subscription** — it lacks the proprietary Google API keys official Chrome ships with, so `pushManager.subscribe()` fails with "push service not available". Any future automated testing of this flow needs `chromium.launchPersistentContext(dir, { channel: 'chrome' })` to use a real installed Chrome, not the default bundled browser. Incognito/ephemeral contexts don't work either — Chrome disables the Push API there on purpose (`launchPersistentContext`, not `launch`, is required so it's a real non-incognito profile).
- **iOS Safari**: push only fires once TaaDaa is added to the home screen (iOS 16.4+) — a regular Safari tab will never receive one. `NotificationToggle.tsx` no longer states this in its own copy (removed by request, to keep the sidebar toggle to a single line) — still true technically, just not surfaced in-app; don't promise otherwise if asked.
- **Now deployed** — see "Deployment (live)" above for the actual URLs and how redeploys work for each half.

## Cross-Device Sync
Not in the original spec — added after the user noticed a fresh phone install had an empty task list, separate from their desktop's. Deliberately the simplest possible thing that could work, not real accounts:
- **A "sync code" is a shared key for one JSON blob on the backend, not a login.** Whoever has the 6-character code (`generateSyncCode()` in `src/lib/sync.ts`, excludes ambiguous characters like `0/O/1/I/L`) can read or overwrite that blob — there's no password, no ownership check. Fine for a personal app (or one shared with a partner), not a place to add anything sensitive.
- **Whole-blob replace, no merge**: `POST /api/sync/:code` overwrites the *entire* stored `{tasks, projects}` for that code; `GET /api/sync/:code` returns it. Same "simplest sync model" philosophy as reminders in `push.ts` — no field-level conflict resolution. If two devices edit at nearly the same moment, whichever pushes last wins, silently. Acceptable for how infrequently that's likely to happen in solo/couple use; revisit if it becomes a real problem.
- **First device** ("sync this device" in `SyncSettings.tsx`, pinned above the notification toggle in the sidebar) generates a new code and immediately pushes its current tasks/projects up.
- **Joining device** ("have a code?") pulls that code's data and **replaces its own local tasks/projects entirely** — this is the one place in the app with a native `window.confirm()`, a deliberate exception to the "no confirmation dialogs" rule, because unlike routine complete/delete actions this is a rare, one-time, genuinely destructive action (silently discarding whatever was on that device already) that isn't a quiet-undo-toast situation.
- Once a device has a code (stored in `localStorage['taadaa.syncCode']`), `App.tsx` pulls once on mount (replacing local state, showing a brief dry "syncing…" next to the theme toggle — first real use of the spec's "syncing," loading-state voice line) and pushes after every `tasks`/`projects` change.
- **Push is debounced** (`SYNC_DEBOUNCE_MS`, 1500ms) rather than firing immediately on every change, added after finding that `TaskEditModal`'s title/note fields auto-save `onChange` (not `onBlur`) — meaning every keystroke while editing a task used to fire a full `POST /api/sync/:code`. `attemptPush()` in `App.tsx` is the one shared implementation (via `useCallback` + `tasksRef`/`projectsRef` refs that always hold the latest data, so the debounce timer and the online-reconnect handler below don't duplicate the push+retry logic).
- **Failures are surfaced, not swallowed.** `syncStatus` (`'idle' | 'syncing' | 'error'`) drives the header indicator next to the theme toggle: "syncing…" while a push (or the initial pull) is in flight, a persistent "sync failed, retrying…" while one has failed. On failure, `attemptPush()` reschedules itself after `SYNC_RETRY_MS` (15s) until it succeeds — automatic, no user action needed, but now visible instead of `pushSync`'s own try/catch silently returning `false` with nothing showing it ever happened. A fresh edit (new debounced push) or the `online` handler both supersede a pending retry rather than stacking timers.
- Same storage caveat as the rest of `server/data.json`: Render's free tier has no persistent disk guarantee across redeploys, so a sync code's data could theoretically be lost if the backend redeploys at the wrong moment. Each device's own `localStorage` copy is unaffected either way, so worst case is re-pushing from whichever device still has the data.
- **Mount-time push/pull race, fixed** — this was the actual cause of "some tasks are randomly missing" across devices. Both the pull-on-mount effect and the push-on-`tasks`/`projects`-change effect used to fire on mount; the push effect would fire immediately with whatever stale local tasks/projects this device already had in `localStorage` *before* the pull's own in-flight fetch resolved. If that stale push reached the server first, it silently clobbered whatever another device had already synced up — the returning device would then "pull" its own just-overwritten data back, with no error and no visible symptom beyond a device's edits quietly vanishing. Fixed with a `syncReady` flag in `App.tsx`, set only once the initial pull attempt (or its no-code no-op) has resolved; the push effect now checks that flag before running, so nothing pushes until the mount-time pull has had its chance to run first. Verified via Playwright: pre-seeded a second browser context with a stale local task and the first device's real sync code, reloaded, and confirmed both the device's local state and the server's stored blob ended up as the *first* device's data, never briefly clobbered by the stale one.
- **Same-device multi-tab clobbering, fixed** — a related but distinct bug: `useTasks.ts`/`useProjects.ts`/`useShoppingItems.ts` each load once from `localStorage` at mount and write back on every state change, but nothing previously kept a long-lived tab's in-memory copy in sync with what *another* tab or window on the same device wrote in the meantime (e.g. the installed PWA left open alongside a leftover browser tab, or two browser tabs). If tab A added an item while tab B stayed open, tab B's next edit would commit its own stale copy over tab A's newer one — this is what made the shopping list "not even stay on the same device sometimes" (`ShoppingDrawer` remounts `useShoppingItems` fresh each time it opens, making a stale background tab an easy way to lose an item that had just been added elsewhere). All three hooks now also listen for the native `storage` event and adopt the incoming value — that event only fires in *other* browsing contexts, never the one that wrote the change, so it can't loop against each hook's own write-effect. Verified via Playwright: two `Page`s in the same browser context (shared `localStorage`, like two tabs), added an item from each without reloading either, confirmed no item was lost.

## Easter Eggs: Snake & Tetris
**Not in the original spec — an explicit, confirmed scope expansion the user requested by name**, unlike everything else in this file's "refinements only" default. Typing `snake` or `tetris` into quick-add and submitting (or clicking the matching icon next to the quick-add bar) opens a canvas game instead of creating a task — `NeonSnakeModal.tsx` / `TetrisModal.tsx`. Desktop only (`window.innerWidth < 768` check in `App.tsx`'s `handleCommand`; mobile gets a "Desktop feature only" toast) since the fixed modal + arrow-key controls don't translate to touch.
- Both games are self-contained: game state lives in refs (not React state), with React state (`score`, `highScore`, `gameOver`) only updated at the moments the UI actually needs to reflect them. Score/high-score persist per-game in their own `localStorage` keys (`taadaa.snake.highScore` / `taadaa.tetris.highScore`), independent of tasks.
- **"Smoother" means two different things per game, by explicit follow-up correction — don't conflate them:**
  - **Snake** stays on a `requestAnimationFrame` render loop: a fixed-cadence tick timer (`TICK_MS`) still advances the actual grid-locked game state, but every animation frame redraws at display refresh rate with a `fraction` (0..1 progress through the current tick) used to lerp each snake segment from its previous cell to its next one (`prevSnakeRef` tracks pre-tick positions so segment `i` can follow where segment `i-1` used to be) — the classic snake glide.
  - **Tetris's piece fall was reverted back to the original instant, per-tick `setTimeout` loop** (`draw()` takes no fraction, snaps straight to `piece.row`) — an initial RAF-interpolated glide was tried and explicitly rejected ("shouldn't be smoother in terms of falling down... it should fall like it used to before"). What Tetris actually needed smoother was **holding left/right** — that's now DAS (Delayed Auto Shift, `DAS_DELAY_MS`/`DAS_REPEAT_MS` in `TetrisModal.tsx`): the first `keydown` moves once immediately and starts a timer; after `DAS_DELAY_MS` (170ms) it starts auto-repeating `moveHorizontal()` every `DAS_REPEAT_MS` (50ms) until `keyup`, ignoring the browser's own native key-repeat (`e.repeat` guarded out) so the rate is consistent across OSes rather than whatever the browser/OS repeat setting happens to be. Don't reapply the RAF-glide treatment to Tetris's fall if asked to make it "smoother" again — ask which axis (falling vs. held-key movement) first, since this has already been corrected once.
- **Cell size is computed from the viewport**, not a fixed constant (`computeCell()` in each modal, `Math.max(min, Math.min(max, Math.floor((window.innerHeight - 200) / rows)))`, clamped 18–34px for Tetris / 16–30px for Snake) — bigger board on a tall screen, by request. Computed once at mount (`useState(computeCell)`), not re-read on resize; a mid-game resize won't rescale the board, which is an acceptable tradeoff for a short-lived modal game.
- **Docked to the right edge of the screen, not centered** — `fixed inset-0` with a dimmed/blurred scrim (`bg-black/50 backdrop-blur-sm`, click to close) behind an `absolute inset-y-0 right-0` panel (`w-full max-w-xl`) that's full viewport height, so the board fills most of the vertical space rather than sitting in a small centered box. Both games share this exact wrapper structure — keep them in sync if you touch one.
- Restricted to the app's existing accent palette (`#D63C7A`, `#E39BC4`, `#4FBDAE`) plus white/charcoal, per the request — don't introduce new colors here without checking first.
- `Toast`'s `onUndo` prop is optional (was required) specifically to support this "Desktop feature only" notice, which has nothing to undo.

## Scope Rules — Ship Lean

- **Phase 1.5 (done):** Calendar view (week + month) with tag highlighting + workload heat-strip, bigger day cells showing content inline.
- **Phase 3 (done):** Recurring tasks + subtasks.
- **Phase 4 (done):** Dark mode, manual toggle + auto system default.

Cross-Device Sync (see above) was added after v1 shipped and deployed — a real example of the "refinements only" rule below in action: it was scoped to the simplest thing that solved the actual reported problem (one device's data not appearing on another) rather than building toward full accounts/auth.

## Non-Negotiables
- One input box for adding tasks — never a multi-field "new task" form (the toolbar adds icon *shortcuts* on top of the one input, it doesn't replace it with a form).
- No confirmation dialogs for routine actions (delete, complete) — quiet undo toast instead. Task editing follows the same spirit: auto-save on change, no explicit Save button.
- Mobile-first: build and test at mobile width first. Sidebar in particular is mobile-drawer-first, desktop-always-visible-second.
- Whitespace and color do the organizing — avoid adding UI chrome (borders, dividers, icons-for-icons'-sake) to create structure.
- Keyboard-first on desktop — Q / Cmd+K jumps to quick-add.

## Verifying UI Changes
No `chromium-cli` in this environment. Use Playwright directly: install it in the scratchpad directory (not the project's `package.json`) with `npm install playwright` + `npx playwright install chromium`, then drive the dev server with a small script. Always check both a mobile viewport (~390px) and a desktop viewport, and check `page.on('console')` / `pageerror` for silent failures. For anything touching push notifications specifically, use a real installed Chrome via `channel: 'chrome'` + `launchPersistentContext` (see Push Notifications caveats above) — the default bundled Chromium cannot complete a real subscription.

**Process hygiene:** dev servers started with `(nohup npm run dev -- --port 5183 &)` don't always die cleanly between sessions — if a port is unexpectedly "in use," check for and kill stale processes (`Get-NetTCPConnection -LocalPort <port> -State Listen` + `Stop-Process` in PowerShell tends to be more reliable than `lsof` in this Windows/git-bash environment) before assuming the running server has your latest code. A stale zombie server on the port you *think* you're testing against, silently serving old code, cost real debugging time this session.
